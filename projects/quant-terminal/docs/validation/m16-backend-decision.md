# M16 isolation backend decision (2026-09-30)

## Decision

Implement `isolated_python` behind a **verified WSL 2 Linux-container backend**. Podman 5.8.3 was selected and installed on this Windows 11 Home host after the initial candidate review. Keep it disabled until a working WSL machine, capability probes, hostile-workload tests, full regression, and independent security review pass. WSL 2 by itself is not an isolation backend: its normal configuration exposes Windows drives and Windows process interoperability to Linux code. The container must receive only a purpose-built immutable Python image and per-run, narrow input; it must never mount the repository, user profile, runtime state, container socket, WSL filesystem, or credentials. The backend is an implementation choice, not a claim that M16 already passes.

The selected runtime must enforce non-root execution, `--network none`, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges`, a verified seccomp profile, private cgroup/process namespace, `--pids-limit`, `--memory` (with swap behavior checked), CPU quota, `--ulimit`, and a size-bounded `--tmpfs` scratch area. No `--privileged`, `--network host`, added devices, published ports, host path bind mounts, or container socket mount. Verify the effective configuration with `podman inspect` and hostile probes; command-line flags alone are insufficient evidence. See [Podman run](https://docs.podman.io/en/latest/markdown/podman-run.1.html).

The trusted Windows scheduler should stage a versioned, bounded request and immutable data snapshot in a dedicated, disposable location, launch the container by an argument array (never a shell command), pass data by a validated stream or tightly scoped copy, and accept only bounded JSON/protobuf-like typed intents. Trusted code owns accounting, risk, result storage and any later broker gateway. A child must never receive the API's DB path or file descriptors. A pinned image digest, runtime version, exact controls and dependency hash belong in capability diagnostics and each run manifest. The scheduler must reject admission if any control is absent, if a control probe fails, or if Docker is unreachable; it must never fall back to an ordinary Windows subprocess.

**Lifecycle needs separate proof.** A Podman client process dying is not proof that its container dies. Podman's `--timeout` is enforced by conmon independently of the client, but cancellation and restart recovery still need per-job container IDs, `--restart no`, and reconciliation that enumerates and kills orphaned labeled containers before accepting new jobs. Prove abrupt scheduler death, descendant cleanup, cancellation and lease release in the M16 hostile suite. If a reliable independent lifetime bound cannot be demonstrated, this backend still fails the contract. Container resource controls also do not automatically enforce total writable-layer bytes or file count, so use a read-only root with bounded tmpfs, cap output in the protocol, and test scratch exhaustion explicitly.

## Host observations

Read-only PowerShell probes on 2026-09-30 returned `Microsoft Windows 11 Home`, 64-bit, build `26200`, with `HyperVisorPresent=True`. `wsl --status` and `wsl --list --verbose` said WSL was not installed. `Get-Command` found `wsl.exe` but no `docker`, `podman`, QEMU, or VMware command. This PowerShell token is **not elevated**. `Get-WindowsOptionalFeature -Online` failed with “requested operation requires elevation,” so the optional-feature states remain unverified. No software installation or reboot was performed for this decision. Earlier capability evidence is in [m16-capability-audit.md](m16-capability-audit.md).

Microsoft's [WSL installation guide](https://learn.microsoft.com/en-us/windows/wsl/install) says to run `wsl --install` from an administrator PowerShell and restart. Its [command reference](https://learn.microsoft.com/en-us/windows/wsl/basic-commands) documents `--no-distribution` and `--web-download` options. Docker's [Windows installation guide](https://docs.docker.com/desktop/setup/install/windows-install/) describes a per-user WSL 2 backend that normally needs no administrator rights for Docker Desktop itself, but WSL 2 must already be enabled and WSL version must be at least 2.1.5. The same page says Home editions can run Linux containers, while its edition-specific requirement table lists Pro/Enterprise/Education; treat actual installation and a Linux-container probe on this Home edition as a required compatibility check rather than assuming support. Docker Desktop licensing must also be checked against the real firm's use; [Docker's license page](https://docs.docker.com/subscription-billing/desktop-license/) distinguishes personal/small-business use from larger commercial organizations. Agent-role count is not evidence of actual employee count.

## Alternatives and limits

| Candidate | Finding | M16 decision |
| --- | --- | --- |
| Bare WSL 2 Python | Linux environment normally interoperates with Windows files/processes; it does not supply the required narrow file/network boundary. [Microsoft interop docs](https://learn.microsoft.com/en-us/windows/wsl/interop) | Reject as execution sandbox. |
| Docker Desktop WSL 2 Linux containers | Well-documented namespaces, seccomp and cgroup controls; viable after WSL install and compatibility/security proof. WSL Docker VM is accessible to the host user; Docker states WSL security is weaker than Hyper-V for strict isolation. [Docker WSL security](https://docs.docker.com/desktop/features/wsl/), [ECI limitations](https://docs.docker.com/desktop/enterprise/hardened-desktop/enhanced-container-isolation/limitations/) | First implementation target, conditional on complete M16 suite. |
| Podman machine | Official Podman docs require a Linux VM for containers on Windows and describe rootless mode. [Podman machine](https://docs.podman.io/en/stable/markdown/podman-machine-init.1.html) | Fallback if Docker Home compatibility/licensing blocks; still requires WSL/VM setup and the same proofs. |
| Native AppContainer plus Job Objects | AppContainer is a recognized Windows boundary, but this repo has no restricted-token launch, capability policy, ACL design, quotas or hostile proof. Microsoft's new process-sandbox API is [experimental](https://learn.microsoft.com/en-us/windows/win32/secauthz/createprocessinsandbox). | Defer; greater implementation and verification risk than Linux containers for Python. |
| Docker Hyper-V backend / Windows Sandbox | Docker recommends Hyper-V plus Enhanced Container Isolation for maximum desktop isolation, but Home lacks the requisite Hyper-V backend; ECI is a Business feature. [Docker ECI limits](https://docs.docker.com/desktop/enterprise/hardened-desktop/enhanced-container-isolation/limitations/) | Not the immediate Home-host path. |

## Installation and acceptance sequence

1. An elevated administrator enables WSL 2; restart if required. Verify `wsl --version`, `wsl --status`, optional features, and a WSL 2 distro/engine before implementation proceeds. An install command returning successfully is not proof of enforcement.
2. Install and launch a supported Linux-container runtime. Capture version, edition, backend, container probe results and licensing status. Keep runtime API/socket unavailable to strategy containers.
3. Implement the fail-closed backend and versioned protocol under [m16-security-contract.md](../m16-security-contract.md). Add independent lifetime control, measured limits, audit and structured reasons.
4. Run all 16 cases in [m16-test-plan.md](m16-test-plan.md) on this actual host. No skipped hostile case can count as a pass. Run the full repository checks and independent security review; only then update [m16-security-gate.md](m16-security-gate.md) to PASS.

Until then, arbitrary Python stays disabled and only the current trusted built-ins run. This decision does not authorize broker orders or strategy forward testing.
