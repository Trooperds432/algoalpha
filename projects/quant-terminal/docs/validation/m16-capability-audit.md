# M16 Windows isolation capability audit (2026-09-30)

**Recommendation: BLOCK the M16 hostile-strategy exit gate on this host.** Retain the current trusted, built-in strategy allowlist. This is a read-only capability and source audit, not an implementation or penetration test. It does not downgrade the passed M13–M15 research gates and does not claim the existing worker path executes arbitrary strategies.

## Contract and current boundary

The owner's M16 objective is to prepare for arbitrary Python strategies with CPU and memory limits, timeouts, restricted filesystem, isolated dependencies, denied network, controlled secrets, reliable process termination, and audit logging. Its exit gate requires a crashing or maliciously resource-intensive strategy to be unable to crash the terminal or expose secrets (`docs/sources/owner-brief.txt:1414-1440`). `AGENTS.md` and `docs/security_model.md` explicitly limit pre-M16 execution to trusted local strategies; process separation, frozen objects and timeouts are not an adversarial sandbox.

`ResearchRuntime.prepare` accepts only names in `_PARAMETERS`, and `ResearchRuntime.strategy` verifies the corresponding `builtin.<name>.v1` identity (`src/quant_terminal/application/runtime.py:169-172,298-301`). The built-ins live in `src/quant_terminal/backtesting/strategies.py`; no arbitrary source loader was identified in the reviewed application path. `JobManager` starts a separate Python child per accepted research job with at most three concurrent workers and a 1–3600-second wall timeout (`application/jobs.py:215-220,263-284`). It passes an allowlisted environment rather than ambient broker/model credential variables, uses a separate runtime directory, kills an expired/cancelled direct child, and preserves failed/interrupted journal states (`jobs.py:215-345`). `worker.py` watches the scheduler process and exits after parent death. These are useful reliability controls for trusted jobs.

They do **not** restrict Python code that could be introduced later: the child runs as the same Windows user, with `cwd` at the writable project root and `PYTHONPATH` pointing at source; there is no OS filesystem or network boundary, restricted token, memory/CPU quota, dependency enclosure, or demonstrated process-tree kill. The direct `Popen.kill()` target would not by itself terminate descendants created by hostile code. An environment allowlist avoids accidental variable inheritance, but code under the same user can still read user-accessible files and may access other processes or credential stores. `stdin/stdout/stderr=DEVNULL` also means sandbox diagnostics must be designed deliberately rather than inferred from worker console output. This risk is **conditional** on admitting untrusted code; current public research requests remain restricted to built-ins.

## Required design and evidence before an adversarial PASS

Microsoft documents an experimental `Experimental_CreateProcessInSandbox` API exported by `processmodel.dll`; its export is present on this host. The API documentation explicitly says it is subject to change, and an export alone does not establish that a policy can be launched and enforced here. Microsoft's open-source MXC project supports several Windows containment backends, but its own current README warns that preview policies can be overly permissive and must not be treated as security boundaries. Therefore neither the API export nor an untested MXC install is an acceptable M16 gate substitute. Sources: [Microsoft sandbox API documentation](https://learn.microsoft.com/en-us/windows/win32/secauthz/createprocessinsandbox), [Microsoft MXC README](https://github.com/microsoft/mxc#readme).

1. Put all submitted Python strategy code behind an explicit **disabled-by-default** admission path; preserve the built-in path. Use a narrow, versioned data/intent protocol and reject pickle or executable objects over the boundary. Strategy callbacks receive only clock-bounded market observations and return intents; the host owns fills, ledger and risk.
2. Build a child process with a restricted security token or tested AppContainer identity, dedicated scratch directory and ACLs, read-only minimal runtime/dependencies, no access to the project, runtime store, user profile or broker secrets, no inheritable privileged handles, and no network capability. Availability of `CreateAppContainerProfile` is insufficient: prove profile/token creation, process launch and denied accesses on this Windows edition. If this cannot be made testable and reliable, use a separately installed, verified VM/container host or leave untrusted strategy execution unsupported.
3. Attach the child before its first instruction to a Job Object with kill-on-close, process count, memory and CPU limits, plus a wall timer. Verify descendant termination, scheduler death, cancellation, timeout, allocation exhaustion, process spawning and repeated failures without losing the journal lease. Bound input/output, scratch disk and artifact size separately; Job Objects do not impose filesystem or network policy.
4. Keep all broker credentials and network-capable broker components outside the strategy boundary. The current environment allowlist remains defense in depth, not a substitute for token/ACL isolation. Log admission identity, code/dependency hashes, effective limits, denial/termination reason and resource use, with redaction and immutable outcome status.
5. Run hostile fixtures that attempt file reads/writes outside scratch, outbound network, environment/user-profile and secret access, child spawning, memory/CPU/disk exhaustion, infinite loops, crashes and malformed protocol messages. Require the host to remain responsive, protected files/secrets inaccessible, descendants gone, no successful partial result, and exact replay of the trusted Golden Quant suite. Independent review and the full gate checks remain necessary.

**Verdict:** specification readiness is partial (the required boundary is defined; no isolated arbitrary-code runner exists). Engineering security gate is **BLOCK** for untrusted Python on the audited host. Continue trusted research only until an implemented boundary passes the hostile tests above. No claim about real broker or forward-test safety is made.
