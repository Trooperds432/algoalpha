# M15 independent performance review (2026-09-30)

**Scope:** Read-only review of the M14-passed Python data, event-loop, and optimization paths. This is an input to M15 profiling, not an M15 gate decision. No production code, tests, broker state, or research results were changed.

## Fresh evidence

Environment: Windows, project `.venv` Python, existing immutable 43-bar ETF-DEMO snapshot `26c1cf1b4e3b43c5188e7625c21cfd842d0331d64b5d61abab418a11bb33ecd7` in the M14 synthetic runtime. A direct 20-call `perf_counter` sample found `load_snapshot`: 5.378 ms/call; `query_bars` for all 43 bars: 24.299 ms/call; and `DataFeed.history(count=5)`: 24.198 ms/call. This small sample demonstrates fixed overhead and should not be extrapolated to large datasets or treated as a stable SLA. A separate 30-call `cProfile` run of `history(count=5)` recorded 0.548 seconds / 694,351 calls; the largest cumulative entries included 30 DuckDB connections (0.243 seconds), 30 full snapshot loads (0.183 seconds), and 2,580 bar-row conversions (0.125 seconds). Profiling overhead changes the absolute timings.

## Findings and safe directions

1. **High-confidence, high-impact candidate: repeated full validation and query setup.** `DatasetStore.query_bars` calls `load_snapshot` on every request (`data/storage.py:458`), which hashes and reads the entire Parquet file, builds every `Bar`, checks every row and canonical hash (`:390-445`), then opens a new in-memory DuckDB connection and materializes the selected rows (`:475-490`). `DataFeed.history` invokes that path on each strategy lookup (`data/feed.py:45-58`); `MovingAverageCross` and `SimpleMomentum` use `StrategyContext.history`. The 43-row sample above directly supports the overhead. Profile 1k/10k/100k-bar datasets and a moving-average backtest before changing it. A bounded, run-scoped verified snapshot handle or validated read cache is a candidate, provided it still detects changed source bytes before a run and never exposes future bars to strategies. Reusing a connection or selecting only the requested tail could help, but retain `available_at`, `end`, and clock visibility filters after any pushdown. Do not replace immutable integrity checks with a permanent unchecked cache.
2. **Memory/throughput candidate, unmeasured at scale:** `import_csv` reads all rows, `_import_rows` holds row dictionaries, `Bar` objects and a full canonical byte string; `load_snapshot` again holds a full Arrow table, Python row dictionaries, `Bar` tuple and canonical bytes (`data/storage.py:247-253, 279-335, 424-444`). `BacktestEngine.run` merges and sorts all selected bars into one tuple, and accumulates NAV points and fills (`backtesting/engine.py:150-174, 241-251`). The code establishes multiple resident copies, but peak RSS has not been measured. Benchmark peak process RSS with larger deterministic data; if limiting memory, stream validated chunks or merge sorted instrument iterators while preserving the `(available_at, instrument_id, start)` ordering and identical batch semantics.
3. **Event-loop candidate, conditional on an active-order benchmark:** `broker.orders.snapshots()` is repeatedly called within each observed-time batch and each proposed intent (`backtesting/engine.py:258-276, 390-425`), and the order registry constructs all snapshots (`orders/lifecycle.py:128`). This can turn order-heavy runs into repeated work; it is not yet measured as a bottleneck. A per-batch local snapshot or indexed active-order view may be safe only if invalidated immediately after submit, reject, cancel and fill. A stale view would change cash reservations, short-sale protection, and order lifecycle outcomes.
4. **Optimization throughput candidate, conditional on campaign measurements:** `run_optimization` enumerates the full bounded candidate tuple before evaluation and runs trials serially (`optimization/engine.py:151-219`; `optimization/models.py:192-228`). Serial evaluation plus durable per-trial recording establishes deterministic order and retention. Profile candidates/second and peak RSS at multiple budgets first. Process parallelism can be considered only with isolated worker state, stable candidate indices, deterministic result ordering, and durable recording of every eligible, infeasible or failed trial. Do not change the sampler, candidate ordering, fingerprints, or resume cursor to gain speed.

## Economic and correctness invariants for every proposed optimization

Compare a reference run and optimized run on the same pinned snapshots, configuration, strategy source and seed. Require exact Decimal values and ordered identity for fills, order transitions, position/cash ledger, NAV timestamps and values, commission/slippage, benchmark, analytics metric status/reason, and result fingerprint. Preserve next-bar execution, participation/price/fee rules, cash reservations, risk rejection, and reconciliation error of zero. Check multi-asset equal-`available_at` ordering and final-boundary liquidation. For feed changes, prove bars with `available_at` or `end` beyond the simulation clock remain inaccessible, including walk-forward in-sample versus out-of-sample isolation. For optimization changes, require identical candidate order, per-trial records/status, rankings, resume behavior and failure retention. Retain the existing Golden Quant fixtures; any changed expected financial output requires an explicit explanation and approval under `AGENTS.md`.

## Suggested M15 benchmark matrix

Use deterministic synthetic daily datasets of 1k, 10k and 100k bars, with 1 and several instruments; no broker connection. Measure import time, cold and warm snapshot load, narrow/full/tail query, feed history at multiple counts, peak RSS, no-order and order-heavy backtests (bars/sec), and 10/100-trial optimization campaigns (trials/sec). Record hardware, Python/library versions, input hashes, strategy/config IDs, wall-clock distribution across repeated runs, peak memory, and exact financial output fingerprints. Profile under the same conditions before selecting a change. The present 43-bar measurements establish only the repeated-query bottleneck, not a scalability target or production capacity.
