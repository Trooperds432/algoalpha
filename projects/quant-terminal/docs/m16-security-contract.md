# M16 security and strategy-isolation contract

## Objective and current boundary

M16 prepares the terminal to execute owner-supplied Python strategies without giving strategy code the authority of the API, job scheduler, experiment store, or a future broker. The current `JobManager` launches a trusted worker process with an allowlisted environment and a wall-clock timeout. That process still shares the host account, source tree and runtime paths; it is **not** a sandbox. The three built-in, owner-reviewed strategies remain the only executable strategies until an independently verified isolation backend meets this contract. Availability of a subprocess, Python import restriction, read-only strategy context, or package virtual environment never changes that classification.

The first trust boundary is between API/CLI requests and the trusted scheduler. The second, stronger boundary is between scheduler and arbitrary strategy code. Dataset bytes, strategy source, installed dependencies and return values are untrusted at that second boundary. Experiment metadata and ledger writes belong to trusted code. Agent identifiers only attribute work; they do not authenticate it. M16 does not authorize paper sessions, broker calls, order submission or live credentials.

## Decision and proposed interfaces

The trusted scheduler chooses one of two explicit execution modes: `trusted_builtin` for the existing catalog or `isolated_python` for arbitrary strategy source. The latter may be advertised or accepted only when an isolation-backend capability probe and its hostile-workload acceptance suite have passed on the current platform. Unsupported hosts reject `isolated_python` before staging source or claiming a job; they never silently run it as `trusted_builtin`. A backend reports its identity, version, enforced limits and probe result in local diagnostics and the run manifest. A process handle alone is not an isolation claim.

The isolation backend accepts a validated, size-bounded strategy package or registered source hash, an immutable point-in-time data slice, a deterministic seed, a declared dependency set, and a budget. It returns bounded typed order intents and diagnostics over a versioned, validated protocol. It cannot write ledger entries, publish artifacts, change risk configuration, or invoke a broker. The trusted side validates every returned intent against the ordinary strategy, risk and execution contracts before any accounting changes. A malformed, oversized, nonfinite or unexpected response fails the job. No pickle, dynamic import of host paths, executable object deserialisation, or arbitrary host command is used as the protocol.

The initial implementation invokes one fresh container per as-of observation. All rows in that request are already visible; no future row may be staged in the worker interpreter, including through an otherwise hidden Python object. `IsolatedStrategy` copies an explicit market-field allowlist through the trusted feed's as-of access. It resolves instrument metadata and validates proposals on the host, and the normal engine still performs risk and cash-reservation checks. Cross-instrument proposals are rejected until they have separately priced observations. Public API/CLI source admission remains disabled; operator containment tests and the internal bridge do not grant public submission authority.

Dependency isolation means packages are pinned, locally resolved and verified before admission; strategy code cannot install packages, load arbitrary native extensions, or modify the dependency environment at runtime. If native code or unsafe runtime facilities cannot be excluded by the chosen backend, the same OS isolation and resource limits must contain them. Admission policy and dependency hashes are recorded with experiment provenance. A hash mismatch rejects the run.

The initial dependency set is the standard library in a digest-pinned Python image. Nonempty third-party dependency declarations reject before launch. Standard-library FFI, shells and descendants remain inside the same OS boundary; they do not create an import-based security boundary. WSL on this host requires a native x86-64 seccomp profile without compatibility architectures; its default-deny syscall rules remain enforced and its effective profile is recorded by the backend.

## Enforced authority and budgets

An `isolated_python` process has a fresh, nonprivileged identity or equivalent OS/container confinement. It receives only the minimal read-only source and data mount/copy plus a bounded scratch directory. The project tree, user profile, runtime state, API database, agent files, credential stores, and arbitrary host paths are inaccessible. Path resolution must account for symlinks, junctions/reparse points, `..`, absolute paths and alternate path syntax. Scratch storage has a byte/file-count limit and is destroyed after the run. Outputs cross the boundary through the validated protocol, not by allowing the sandbox to write directly to the artifact store.

The first Podman backend supports **zero writable scratch**: `scratch_bytes=0` and `scratch_files=0`. Positive scratch budgets reject because the tested remote mount parser cannot enforce an inode quota. The root filesystem is read-only, automatic writable temporary mounts are disabled, and shared-memory IPC is disabled. No host-path mount is permitted. This is an enforced support limit, not a Python file-access restriction.

Network access is denied at the OS/container boundary, including loopback, DNS, IPv4, IPv6, and child processes. The worker has no access to host IPC endpoints or inherited handles that lead back to the API. Environment, command line, current directory, standard streams and mounts contain no broker, model, Paperclip or cloud secrets. Secrets remain in a separate trusted gateway for later milestones; strategy code receives no token, signing capability or broker client. The scheduler redacts sensitive values from errors, events, logs and exception traces, and caps log volume.

The scheduler enforces explicit limits on elapsed wall time, CPU time, resident memory, process count, open handles/files where available, scratch bytes and output bytes. Defaults and maximum overrides are documented in configuration and copied into the manifest; an unset or unenforceable mandatory limit rejects `isolated_python`. Limits cover descendants, not just the parent PID. Timeout, cancellation, process crash, OOM, over-budget output and scheduler shutdown terminate the entire sandbox process tree and reap it before a job reaches a terminal status or the scheduler lease is released. A failed kill is an unhealthy scheduler condition that blocks new submissions until reconciliation. A dead scheduler must not leave an independently executing strategy; the backend must enforce parent-death/lifetime ownership independent of cooperative Python code.

## Failure, audit and reproducibility

Admission, capability probe, launch, limit violation, cancellation, crash, termination and cleanup produce structured audit events with UTC timestamp, job/run identity, strategy/source hash, backend/version, budget, outcome and a stable reason code. Logs never include strategy source, credentials, full environment or raw untrusted output by default. Audit writes are trusted-side and append-only within the existing event model; a failure to record a required security event blocks admission or fails the job rather than silently continuing. Operator diagnostics may state which control failed without revealing protected values.

Any boundary failure yields `failed`, `cancelled` or `interrupted`, never `succeeded`. A partial result is not presented as a verified experiment. Immutable completed run artifacts remain intact, while temporary scratch is removed after process death. Replays require the same source, dependency and data hashes, engine version, seed, budget and backend identity; a changed environment produces an explicit non-reproducible/incompatible outcome. Existing trusted financial semantics and golden fixtures must remain unchanged.

The M16 gate cannot be marked passed for arbitrary Python on a platform where OS controls are unavailable or untested. It may document a platform as unsupported and keep the feature disabled, but that limitation must be visible in CLI/API/UI capability reporting and the milestone report. Windows process boundaries, environment filtering and timeout alone never satisfy this exit gate.
