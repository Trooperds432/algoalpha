# M10 walk-forward validation contract

## Objective

Evaluate parameter selection using strictly out-of-sample (OOS) windows. For each window, optimize on in-sample (IS) data only, freeze the selected parameters and source identity, execute exactly once on the following OOS interval, retain both records, then advance. Support fixed-length rolling IS and anchored/expanding IS. M10 is research validation; it does not submit orders or qualify capital for live use.

## Window plan

An immutable `WalkForwardSpec` contains a unique experiment ID, UTC evaluation interval, training duration, test duration, window step, mode, time/calendar basis, selected M2 snapshot identities, and a complete fixed M8 experiment configuration identity. The identity pins strategy ID/name/source, project source, Git revision, engine and dependency lock, datasets, currency, capital, seed, backtest and analytics settings, benchmark, and execution assumptions; only dates and selected parameters vary by window. M10's first implementation uses fixed-duration UTC windows and requires step equal to test duration, preventing overlapping or missing OOS intervals. IS end equals OOS start. Rolling IS uses the requested fixed training duration; anchored IS begins at the original interval start and expands to each OOS boundary. The final OOS interval may be shorter only when it reaches the declared overall end. No window is emitted without a complete training period and positive OOS period.

## Execution boundary and leakage controls

The optimizer callback receives only a typed window with the IS bounds and immutable base identity. It runs a bounded M9 optimization against those bounds and returns a detached `FrozenSelection`: exact chosen parameters, strategy/source identity, M9 campaign fingerprint, selected M8 run ID, and typed IS metrics. The OOS callback receives the window and that frozen selection, then returns a typed M8 OOS run identity, exact BacktestResult, and M6 metrics. The IS optimizer is never called with OOS bounds/data. Each result interval and every NAV/order/fill timestamp is checked against its respective half-open window. OOS starts at IS end. A window audit records both intervals, source M2 snapshots, the exact selection identity, the IS campaign ID, and the OOS run ID. The orchestration API accepts a caller-owned durable recorder plus a verified contiguous completed-window prefix and cursor for resumption; storage and recovery policy remain with that adapter.

The integration test instruments `DatasetStore.query_bars` during the optimizer phase and fails if any query's upper bound exceeds the window's IS end; during OOS execution it verifies the OOS bounds. A caller remains responsible for using the supplied bounds in its trusted adapters. The trusted OOS adapter must schedule end-of-window liquidation against the final eligible OOS close, using configured execution costs and liquidity, and fail if no executable mark or capacity exists. The core rejects OOS runs with residual positions or active orders at the boundary. Each later OOS run starts with the prior run's terminal equity as cash; the first uses pinned experiment capital. M10 never passes OOS observations to the optimizer callback.

## Output and stitching

Retain all M9 trials in their M9 journals, frozen selected parameters for every window, M8 IS and OOS run IDs, fingerprints, and complete IS/OOS metric maps. Produce a deterministic window table, selected-parameter stability summaries, metric degradation (`OOS - IS` when both values are available), and a stitched OOS-only NAV path. The stitched path contains each OOS start baseline and OOS result checkpoints only; it uses actual NAV after priced boundary liquidation and prior-terminal-equity funding, without rescaling window results. It never includes IS NAV observations. Return-only gaps/missing metrics remain explicit and are not zero-filled. Repeated identical specifications/adapters must reproduce the window plan and exact OOS economic fingerprints.

## Failure and resume

Validate the complete window plan before starting. Each completed M9 campaign and M8 OOS run is immutable and retained. Selection or result identities that do not match the window's IS/OOS interval, data, source, or fingerprint fail closed. OOS runs that are not funded according to the boundary policy or retain positions/active orders fail closed. Cancellation is allowed only between windows; the caller-owned durable recorder retains the exact contiguous completed-window prefix and the next cursor. Resume requires the identical spec fingerprint and verifies every prior selection/OOS identity and funding link before proceeding. Data-integrity and storage failures stop the workflow; a failed window is visible and cannot be labeled complete.

## Verification and exit gate

Test rolling/anchored boundaries, clipped final period, invalid durations/steps, detached immutable selection, strict IS/OOS timestamp boundaries, no OOS query during M9 optimization, OOS result identity mismatch rejection, a non-flat OOS adapter that executes its final close at the configured market price with commissions and participation limits, zero-capacity liquidation failure, flat-boundary enforcement, prior-terminal funding continuity, and OOS-only recorded NAV points, degradation and missing metrics, parameter stability, repeat identity, cancellation/resume prefix verification, and fail-closed recorder behavior. The exit gate is a stitched equity path built only from genuine later-window results and independently reviewed leakage evidence.
