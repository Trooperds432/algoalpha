PROJECT NAME
Quantitative Research & Trading Terminal

MISSION
Build a professional-grade, Python-native quantitative trading research terminal
that provides a workflow comparable to MultiCharts/AmiBroker for systematic
strategy research while using modern Python architecture.

The system must allow users to:

1. Write trading strategies in Python.
2. Backtest them against historical data.
3. Model realistic execution.
4. Analyse portfolio and trade performance.
5. Optimise strategy parameters.
6. Perform rolling and anchored walk-forward optimisation.
7. Perform Monte Carlo and robustness analysis.
8. Compare experiments.
9. Detect overfitting and common backtesting biases.
10. Produce professional quantitative reports.
11. Eventually run the same strategy through paper and live broker adapters.

The product should ultimately combine:

MultiCharts/AmiBroker-style research workflow
+
Python quantitative ecosystem
+
LEAN-style execution/reality modelling
+
vectorbt-style high-throughput research
+
pyfolio-style analytics/tear sheets.

II. NON-NEGOTIABLE ENGINEERING PRINCIPLES
============================================================

PRINCIPLE 1 — CORRECTNESS BEFORE SPEED

A slow correct backtest is more valuable than a fast incorrect backtest.

Never optimise code before establishing reference behaviour.

PRINCIPLE 2 — STRATEGIES EXPRESS INTENT

Strategies must never directly modify:

cash,
positions,
fills,
portfolio NAV,
commissions,
margin,
or broker state.

A strategy may generate an OrderIntent.

The execution system determines what actually happens.

Required conceptual flow:

Market Data
    ↓
Strategy
    ↓
Order Intent
    ↓
Risk Validation
    ↓
Broker / Execution Simulator
    ↓
Order
    ↓
Fill(s)
    ↓
Portfolio Accounting
    ↓
NAV / Positions / Cash
    ↓
Analytics

PRINCIPLE 3 — SINGLE STRATEGY API

The same strategy interface should eventually support:

historical backtesting,
optimisation,
walk-forward testing,
paper trading,
live trading.

Do not create separate strategy implementations for these modes.

PRINCIPLE 4 — REPRODUCIBILITY

Every experiment must be reproducible.

Every run must record:

run_id
strategy identifier
strategy source hash
Git commit
engine version
dataset version
data snapshot
parameters
start/end date
initial capital
random seed
execution assumptions
commission model
slippage model
calendar
timezone
Python version
dependency/environment version
timestamp
machine/runtime metadata where appropriate.

PRINCIPLE 5 — IMMUTABLE ECONOMIC RECORDS

Orders, fills, trades and experiment metadata should be immutable once written.

Corrections should create new events rather than silently rewriting history.

PRINCIPLE 6 — NO LOOK-AHEAD

The strategy must never be able to access information unavailable at the
simulated timestamp.

Enforce this architecturally rather than relying on strategy authors to behave.

PRINCIPLE 7 — SEPARATION OF CONCERNS

Maintain separate modules for:

data
strategy runtime
execution
brokerage
portfolio/accounting
risk
backtesting
optimisation
walk-forward
Monte Carlo
analytics
reporting
experiments
API
UI
live trading.

PRINCIPLE 8 — EXPLICIT ASSUMPTIONS

Never silently choose financial conventions.

Examples:

Sharpe annualisation
risk-free rate
trade matching method
turnover definition
slippage reference price
fill timing
corporate action treatment
timezone
calendar
VaR convention.

These must be configurable or explicitly documented.

PRINCIPLE 9 — NO FALSE PRECISION

Results produced using OHLCV bars must not pretend to know intrabar event
ordering unless a documented assumption/model determines it.

PRINCIPLE 10 — BACKTEST/PAPER/LIVE PARITY

Architect interfaces so that historical execution and live execution can
implement the same contracts.

============================================================

The finished application should answer, reproducibly:

"What would this strategy have done?"

"Exactly how were orders filled?"

"What assumptions produced this result?"

"What did commissions and slippage cost?"

How I would actually sequence the project

I would treat the roadmap as four releases rather than one enormous build.

Release 0.1 — Trusted Backtester should cover Milestones 0–8. This is the most important release. By its end, you should be able to write a Python strategy, run it on point-in-time historical data, simulate orders and costs, obtain a correct portfolio ledger, calculate professional statistics, generate a tear sheet, and reproduce the run exactly. Do not build the polished React terminal until this works.

Release 0.2 — Quant Research Terminal should cover Milestones 9–14. This adds optimisation, walk-forward analysis, Monte Carlo, robustness analysis, the API/CLI and finally the professional GUI. This is where the application starts to resemble your intended "MultiCharts for Python" product.

Release 0.5 — Research-to-Trading Platform should cover Milestones 15–18. Only here would I spend significant effort on speed, sandbox arbitrary Python strategies, introduce realtime infrastructure, paper trading and then one live broker adapter.

Release 1.0 — Professional Quant Platform covers Milestones 19–21 selectively. Portfolio optimisation, factor analytics, additional asset classes, institutional risk controls and production hardening become modular extensions rather than changes to the core engine.

The critical point is that v0.1 should already be useful. If you stop development there temporarily, you still have a rigorous Python backtester rather than half of an enormous trading platform.

One addition I would make to the research blueprint

Create a "Golden Quant Test Suite" from the first week and treat it almost like a second product. For example, maintain 20–50 tiny artificial markets covering gaps, splits, dividends, shorts, partial fills, stop orders, limit orders, zero-volatility returns, complete losses, missing bars, leverage and pathological drawdowns. Each fixture should contain mathematically predetermined expected orders, fills, cash, positions, NAV and metrics.

Then require:

No change to the engine, optimiser, data system or accounting system may merge if any Golden Quant fixture changes without an explicit explanation and approval.

That will protect you against one of the most dangerous failure modes in quantitative software: improving or refactoring something and unknowingly changing historical results.

I would also maintain a second differential validation suite against LEAN/Backtrader for deliberately simple strategies where execution assumptions can be made identical. Your own engine remains authoritative for your specified semantics, but unexplained disagreement becomes a defect investigation.

Finally, I would not use MATLAB as the application foundation. Keep the architecture Python-native and introduce MATLAB later behind a ModelAdapter if you want MATLAB models to supply forecasts, covariance matrices, optimisation results or signals. That preserves the value of MATLAB without forcing every backtest through a Python↔MATLAB boundary. This is consistent with the architectural conclusion of the research you commissioned.

The strongest first target is therefore Milestone 0 → Milestone 8, with no live trading at all. Once those gates pass, you have established the trustworthy computational core on which everything else depends.
